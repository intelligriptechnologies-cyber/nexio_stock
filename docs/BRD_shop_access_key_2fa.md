# BRD: Improved UI Auth With Shop Access Key 2FA

## Summary

Create branch `improved_ui_auth` and add a BRD markdown file at `docs/BRD_shop_access_key_2fa.md`.

The feature adds a shop-configurable second-factor login step using a Windows "Nexio Stock Authenticator" app. The existing login screen remains unchanged. After username/PIN login succeeds, the backend checks whether 2FA is required. If required, the frontend shows a second verification step asking for the 6-digit access key generated by the customer's local authenticator.

## Key Requirements

- Do not change the first login screen fields or flow.
- Add a second-factor verification layer after successful credential login.
- Add a new `Shop Master -> Two Factor Authentication` tab for superadmin shop-level control.
- Shop-level 2FA can be enabled or disabled by superadmin.
- If shop 2FA is disabled, shop users log in with the current flow.
- If shop 2FA is enabled, owner/cashier/receiver must complete access-key verification before entering the app.
- Superadmin login also requires its own access key by default.
- Superadmin 2FA can be disabled only from that superadmin user's own profile settings.
- Build a self-contained Windows installer for the customer authenticator so customers do not need to manually install `.NET`.
- Customer-side authenticator should be a tiny Windows GUI app, not a console app.
- Authenticator displays shop name/code, current 6-digit key, and countdown until the next key.

## Implementation Design

- Use a TOTP-style algorithm: secret + time window + HMAC -> 6-digit code.
- Use 5-minute time windows for shop usability.
- The backend does not store displayed codes. It independently recalculates valid codes using the same shop/superadmin secret and server time.
- Shop access key should not literally encode shop ID inside the 6 digits. The backend determines the shop from the authenticated user/session challenge, then verifies the code against that shop's secret.
- Login becomes a two-stage flow:
  - Stage 1: existing credentials are submitted.
  - Stage 2: if 2FA is required, backend returns a pending auth challenge instead of the final app JWT.
  - Stage 3: frontend asks for the 6-digit key and submits it with the challenge token.
  - Stage 4: backend verifies the key and issues the normal JWT.
- Add browser/device registration enforcement for shop users when shop 2FA is enabled.
- Keep superadmin browser login available, but require superadmin access-key verification unless disabled in that superadmin profile.

## Tech Stack

- Backend: existing `FastAPI + SQLAlchemy + Postgres`.
- Web frontend: existing `React + Vite`.
- Customer authenticator: `.NET 8 WinForms`.
- Packaging: self-contained Windows installer or self-contained EXE so `.NET` runtime installation is not required.
- Local secret protection: Windows DPAPI.
- Installer tooling: `WiX Toolset`, `MSIX`, or a simple self-contained publish pipeline first, then formal installer if needed.
- Superadmin generator: separate Windows GUI app with encrypted local master vault.

## Backend/API Additions

- Add shop 2FA settings:
  - `two_factor_enabled`
  - `two_factor_secret_version`
  - `two_factor_rotated_at`
  - `two_factor_required_for_roles`
- Add superadmin user 2FA setting:
  - enabled by default
  - can be disabled only by that superadmin in profile settings
- Add pending auth challenge model:
  - challenge ID/token
  - user ID
  - shop ID when applicable
  - required factor type
  - short expiry
  - consumed timestamp
- Add endpoints:
  - `POST /auth/login` continues first-stage credential login
  - `POST /auth/verify-2fa` verifies access key and issues final JWT
  - superadmin shop 2FA management endpoints under shop maintenance
  - superadmin/user profile endpoint for superadmin 2FA preference
  - device activation/deactivation endpoints for shop machines
- Add audit logs for:
  - 2FA enabled/disabled
  - secret generated/rotated
  - challenge created/verified/failed/expired
  - device activated/deactivated
  - superadmin 2FA disabled/enabled

## UX Requirements

- First login screen remains visually and behaviorally unchanged.
- The second-factor screen appears only when required.
- Second-factor screen should be simple:
  - title: "Enter Access Key"
  - one 6-digit input
  - clear error for expired/wrong code
  - retry action
  - back/logout action
- Shop Master gets a new `Two Factor Authentication` tab with:
  - enable/disable shop 2FA
  - generate/rotate shop secret
  - download customer authenticator installer
  - registered machine list
  - deactivate/reactivate machine
- Superadmin profile gets a 2FA setting section:
  - show current status
  - allow disabling/enabling superadmin 2FA
  - require password confirmation before disabling

## Customer Machine Requirements

- Windows 10 or Windows 11.
- Modern browser: Edge, Chrome, or Firefox.
- Internet access for the web app.
- Correct system date/time with Windows automatic time sync enabled.
- Installed Nexio Stock Authenticator.
- No manual `.NET` installation required because the app is packaged self-contained.
- Stable Windows user profile for local activation storage.

## Risks and Challenges

- A 5-minute code can be shared, so browser/device registration should remain part of shop-user enforcement.
- If a customer-specific installer leaks, it may expose or allow reuse of the shop authenticator unless activation and local protection are implemented carefully.
- Superadmin local master vault is sensitive; compromise could expose all customer shop codes.
- Clock drift can cause valid-looking customer codes to fail.
- Disabling superadmin 2FA must be protected because it weakens the highest-privilege account.
- Recovery flows for reinstalled or replaced machines must be easy for support.

## Test Plan

- Existing login works unchanged when shop 2FA is disabled.
- Login returns pending 2FA challenge when shop 2FA is enabled.
- Final JWT is issued only after valid access-key verification.
- Wrong, expired, reused, or malformed access keys fail.
- Unregistered browser/device fails when shop 2FA is enabled.
- Superadmin login requires access key by default.
- Superadmin can disable own 2FA only after profile/password confirmation.
- Shop Master can enable/disable 2FA and rotate secrets.
- Customer authenticator installer runs on a clean Windows machine without manual `.NET` install.
- Existing checkout, receiving, dashboard, settings, and admin flows continue after final JWT issuance.
